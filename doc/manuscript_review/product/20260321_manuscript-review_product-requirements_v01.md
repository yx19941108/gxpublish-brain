# 审校模块产品需求说明书（V1）

## 一、文档说明

### （一）文档目标

本文档用于定义 `gxpublish-brain` 项目中“审校模块”一期建设范围、业务流程、页面结构、字段规则、权限口径、资源管理、历史审计与验收标准，作为后续设计、开发、测试和验收的统一依据。

### （二）适用范围

本文档适用于以下对象：

1. 产品、研发、测试、实施与验收人员。
2. 出版集团内部使用审校流程的业务部门。
3. 后续基于本模块继续扩展功能的维护人员。

### （三）设计前提

1. 本轮建设为全新审校模块建设，不以现有失败的旧审校业务实现作为设计输入或兼容基线。
2. 本模块复用现有系统的角色、租户、字典、OSS、BPM 待办/已办、流程办理与流程历史能力。
3. 本模块前台统一承载“业务台账、详情、编辑”，实际审批办理入口复用现有 BPM 待办办理页。
4. 本文档中的“审校模块”同时覆盖“审核流程”和“校对流程”两类业务流程。

## 二、建设目标与范围

### （一）建设目标

一期目标如下：

1. 实现出版集团媒体及稿件审校流程的电子化、规范化和可追溯化。
2. 建立统一的审校业务台账，承接新增、查看、跟踪和详情分流。
3. 建立明确的三级串行审批闭环，并支持“持证发起人自动跳过一级审批”。
4. 建立对正文、附件、外链、视频及视频时间标注的结构化承载能力。
5. 建立统一时间线审计能力，确保流程操作、资料变更和审批动作均可追溯。

### （二）一期范围

一期明确纳入以下范围：

1. 业务台账列表页。
2. 新增页。
3. 修改页。
4. 详情页。
5. 与现有 BPM 待办/已办和办理页的集成。
6. 审核流程与校对流程两类流程类型。
7. 固定三级串行审批。
8. 持证发起人自动跳过一级审批规则。
9. 正文、附件、外链、视频与视频时间标注管理。
10. 统一时间线历史审计。

### （三）一期不纳入范围

一期明确不纳入以下内容：

1. 草稿功能。
2. 删除功能。
3. 回收站或恢复功能。
4. 会签、并行审批、加签、减签、转办等复杂审批形态。
5. 动态审批层级。
6. 直接对接稿件主数据系统、媒体主数据系统。
7. Office 文档页内在线预览。
8. 对外链做联网可达性探测。

## 三、角色定义

### （一）发起人

发起人负责新增审校流程、填写表单、提交流程、查看详情、在被退回后修改并再次提交，以及在审批中撤销流程。

### （二）一级审批人

一级审批人根据流程类型与审批链映射规则获取待办，具备查看、修改、审批通过、退回发起人的权限。

### （三）二级审批人

二级审批人根据流程类型与审批链映射规则获取待办，具备查看、修改、审批通过、退回发起人的权限。

### （四）三级审批人

三级审批人根据流程类型与审批链映射规则获取待办，具备查看、修改、审批通过、退回发起人、驳回终止流程的权限。

### （五）历史参与人

历史参与人指曾经办理过该流程的审批人。历史参与人可在业务台账中继续看到该条流程，并可查看完整详情与历史，但不具备当前动作权限。

### （六）系统配置维护人员

系统配置维护人员负责维护审校流程与审批角色的映射关系、持证发起人角色成员、媒体/栏目预设等基础配置。

## 四、业务流程

### （一）主流程

[[FLOWCHART]]

主流程说明如下：

1. 发起人填写审校表单并提交流程。
2. 默认情况下流程依次进入一级审批、二级审批、三级审批。
3. 三级审批通过后流程结束，状态变为“已完成”。

### （二）持证发起人自动跳过一级审批

1. 发起人若具备“持证发起人”专用角色，则在每次“提交”或“再次提交”时由系统实时判定其持证资格。
2. 判定结果为“具备持证资格”时，本次提交自动跳过一级审批，直接进入二级审批。
3. 判定结果仅影响本次提交流转，不作为流程固定属性保存于基本信息区。
4. 历史时间线中必须记录“系统判定发起人具备持证资格，自动跳过一级审批”。
5. 若发起人不具备持证资格，则流程按正常一级审批进入。

### （三）退回、撤销、驳回规则

1. 一级、二级、三级审批人均可将流程“退回发起人”。
2. 被退回后，流程状态为“已退回”，当前节点为“待发起人处理”。
3. 发起人被退回后，必须先修改保存，再单独执行“再次提交”。
4. 发起人可对审批中的流程执行“撤销”，撤销后流程状态为“已取消”。
5. 三级审批人除“通过”“退回发起人”外，还可执行“驳回”，驳回后流程状态为“已驳回”。
6. 被驳回或已取消的当前流程记录不再继续流转。
7. 驳回仅终止当前这条流程记录，不等于永久禁止该稿件未来重新发起一条新流程。

### （四）多人角色场景

1. 审批链映射到的是“审批角色”，而不是单一用户。
2. 若某一级审批角色下存在多名有效成员，则该级审批采用“候选池一人办结”模式。
3. 该级待办对该角色成员可见，由其中任意一名成员办理后本级结束。
4. 一期不增加认领步骤，直接沿用现有待办办理模式。

## 五、状态与节点定义

### （一）流程状态

列表与详情中的流程状态采用以下粗粒度口径：

1. 审批中。
2. 已退回。
3. 已完成。
4. 已取消。
5. 已驳回。

### （二）当前节点

列表与详情中的当前节点采用以下业务文案：

1. 待一级审批。
2. 待二级审批。
3. 待三级审批。
4. 待发起人处理。
5. 流程完成。
6. 流程已取消。
7. 流程已驳回。

### （三）状态展示规则

1. 业务台账列表将“流程状态”和“当前节点”拆成两列展示。
2. “审批中”只表达流程总体处于处理中，不单独说明层级。
3. 层级进展由“当前节点”列承担，例如“待二级审批”。

## 六、信息架构与页面需求

### （一）页面结构

一期页面结构固定为以下五类入口：

1. 业务台账列表页。
2. 新增页。
3. 修改页。
4. 详情页。
5. 复用现有 BPM 待办办理页。

### （二）业务台账列表页

业务台账列表页承担“找流程、看状态、进详情”的职责。

列表默认规则如下：

1. 默认排序为最近更新时间倒序。
2. 默认操作仅保留“详情”。
3. 一期不提供删除操作。

搜索区包含以下条件：

1. 统一关键词搜索，覆盖系统稿件号、外部稿件编号、标题。
2. 流程类型。
3. 所属媒体/栏目。
4. 流程状态。
5. 当前节点。
6. 发起时间区间。
7. 搜索按钮。
8. 重置按钮。

列表默认展示以下列：

1. 系统稿件号。
2. 标题。
3. 流程类型。
4. 所属媒体/栏目。
5. 流程状态。
6. 当前节点。
7. 发起人姓名。
8. 最近更新时间。
9. 详情操作。

### （三）新增页

新增页承担“发起一条新流程”的职责。

新增页规则如下：

1. 发起人填写表单后直接执行“提交”。
2. 一期不提供草稿功能。
3. 提交成功后回业务台账列表页。
4. 新增本身不形成“修改历史”，但必须形成“新增流程”历史记录。

### （四）修改页

修改页承担“修改流程资料”的职责。

修改页规则如下：

1. 只有当前具备修改权的用户才可进入修改页。
2. 发起人在“已退回”场景下可进入修改页。
3. 当前审批人因“可审即可改”原则，在其待办场景下也可进入修改页。
4. 修改页中对附件、外链等流程资料的新增和停用统一处理。
5. 修改保存成功后统一回详情页。

### （五）详情页

详情页是本模块的动作中枢，承担“查看、分流动作、承接资源预览和历史审计”的职责。

详情页包含以下三大区域：

1. 基本信息区域。
2. 流程历史区域。
3. 文件预览区域。

详情页动作展示规则如下：

1. 当前审批人：显示“修改 / 去审批 / 返回”。
2. 被退回的发起人：显示“修改 / 再次提交 / 返回”。
3. 纯查看人：仅显示“返回”。

### （六）BPM 待办办理页

1. 审批动作仍复用现有 BPM 待办办理页。
2. 详情页点击“去审批”后跳转至当前流程对应待办项的办理页。
3. 审批人不在详情页直接完成审批，而是通过现有 BPM 办理页完成“通过、退回、驳回”。

## 七、基本信息区域

### （一）展示结构

基本信息区域采用“双卡片”结构：

1. 流程状态摘要卡片。
2. 稿件基本信息卡片。

### （二）流程状态摘要卡片

流程状态摘要卡片至少展示以下内容：

1. 流程状态。
2. 当前节点。
3. 发起人姓名。
4. 最近更新时间。

### （三）稿件基本信息卡片

稿件基本信息卡片至少展示以下内容：

1. 流程类型。
2. 系统稿件号。
3. 外部稿件编号。
4. 标题。
5. 所属媒体/栏目。
6. 报送部门。
7. 作者。
8. 说明。
9. 正文。

### （四）正文展示方式

1. 正文默认折叠展示摘要。
2. 用户可手动展开查看全文。
3. 正文内容较长时，不应挤压状态卡片与资源区的阅读体验。

## 八、表单字段与校验规则

### （一）字段定义

1. 流程类型。
   - 取值：审核流程、校对流程。
   - 前台统一体验，后台按流程类型解耦审批链与配置。

2. 系统稿件号。
   - 由系统生成。
   - 用户可见但不可编辑。
   - 规则：`SH|JD + yyyyMMdd + 三位流水号`。
   - 审核流程前缀为 `SH`，校对流程前缀为 `JD`。
   - 流水号按流程类型、按日重置。

3. 外部稿件编号。
   - 用户录入。
   - 非必填。
   - 若填写，则在审校模块内全局唯一。

4. 标题。
   - 必填。
   - 最大长度 200。

5. 正文。
   - 必填。
   - 最大长度 20000。

6. 说明。
   - 非必填。
   - 最大长度 1000。

7. 所属媒体/栏目。
   - 下拉可手填。
   - 最大长度 100。
   - 手填值仅保存在当前流程，不自动回写为全局预设。

8. 报送部门。
   - 自动带出。
   - 只读。

9. 作者。
   - 多作者文本字段。
   - 最大长度 200。
   - 仅允许使用中文顿号 `、` 作为分隔。

10. 附件。
    - 支持多个。
    - 视频属于附件的一种。

11. 外部链接。
    - 支持多个。
    - 每条外链包含“链接标题 + URL”。
    - 链接标题最大长度 200。
    - URL 最大长度 500。

### （二）提交校验

提交或再次提交时必须满足以下条件：

1. 正文必填。
2. 附件或外链至少有一种。
3. 视频计入附件。
4. 审批链映射必须完整。
5. 对应审批角色必须存在至少一名有效成员。

### （三）外链校验

1. 同一流程内 URL 不允许重复。
2. 外链只允许合法的 `http://` 或 `https://` 协议。
3. 一期不做联网可达性校验。

### （四）展示与输出规则

所有页面统一遵循以下展示原则：

1. 不展示数据库主键。
2. 不展示英文码或数字枚举原值。
3. 不展示账号，统一展示姓名。
4. 时间统一展示为 `yyyy-MM-dd HH:mm:ss`。
5. 所有枚举与状态统一展示中文业务描述。

## 九、文件预览与视频标注

### （一）文件预览区域总体规则

文件预览区域优先服务视频场景，并补充当前有效附件与外链清单。

该区域按以下结构展示：

1. 视频区优先展示。
2. 当前有效附件清单。
3. 当前有效外链清单。

### （二）视频规则

1. 一条流程可上传多个视频。
2. 多视频时采用“视频列表 + 单播放器”结构。
3. 当前选中视频在主播放器区播放。
4. 一期仅承诺 `MP4(H.264)` 可在线播放。
5. 视频默认大小上限为 1GB，且系统应支持后续配置调整。

### （三）视频时间标注

时间标注模型如下：

1. 开始时间。
2. 可选结束时间。
3. 备注。

时间标注规则如下：

1. 详情页中直接新增和停用标注。
2. 标注操作即时生效。
3. 单个视频下标注列表默认按开始时间正序展示。
4. 点击标注后跳转视频到对应开始时间。
5. 一期不要求自动在结束时间停止播放。

### （四）时间录入格式

系统允许三种合法输入格式：

1. `ss`
2. `mm:ss`
3. `HH:mm:ss`

系统统一归一保存和展示为 `HH:mm:ss`。

示例如下：

1. `5` 归一为 `00:00:05`。
2. `03:07` 归一为 `00:03:07`。
3. `01:02:09` 保持为 `01:02:09`。

### （五）时间校验规则

以下情况必须禁止提交并给出明确提示：

1. 时间格式非法。
2. 结束时间早于开始时间。
3. 标注时间超出视频总时长。
4. 视频总时长尚未识别完成。

系统不对非法时间做自动猜测或自动修正。

## 十、资源生命周期规则

### （一）附件与外链

1. 附件和外链均采用“追加写入”方式，不覆盖历史记录。
2. 当前资源允许被停用。
3. 停用后不再出现在“当前有效资源”列表中。
4. 停用资源仍保留在历史时间线中。
5. 历史中的停用资源仍允许查看或打开，以满足追溯要求。

### （二）视频标注

1. 视频标注采用“追加历史 + 当前可停用”的生命周期规则。
2. 标注一旦新增即进入历史。
3. 标注可被停用。
4. 停用后不再出现在当前有效标注列表中，但仍在历史中可追溯。

## 十一、权限与可见性

### （一）业务台账可见范围

以下任一条件成立时，当前用户可在业务台账中看到该流程：

1. 当前用户是发起人。
2. 当前用户当前拥有该流程的待办审批权。
3. 当前用户历史上已办理过该流程。

### （二）可审即可改

系统遵循“可审即可改”原则：

1. 当某个用户当前拥有对该流程的审批权限时，该用户同时拥有对该流程的修改权限。
2. 除具备当前审批权或被退回的发起人外，其余用户均不可修改流程资料。

### （三）动作边界

1. 修改和“再次提交”必须分为两步。
2. 修改和“去审批”必须分为两步。
3. 不允许“一边改一边直接审批”。
4. 不允许“一边改一边直接再次提交”。

## 十二、流程历史与审计

### （一）展示结构

流程历史区域采用统一时间线模式，自最早到最新排序展示。

### （二）文案风格

历史文案采用自然语言句式，示例如下：

1. 张三新增了流程。
2. 李四修改了标题：旧值 -> 新值。
3. 王五上传了新附件《样片_v2.mp4》。
4. 赵六新增了外链《素材参考链接》。
5. 系统判定发起人具备持证资格，自动跳过一级审批。
6. 钱七退回给发起人：请补充说明。

### （三）必须记录的历史动作

时间线至少记录以下动作：

1. 新增流程。
2. 修改流程信息。
3. 再次提交。
4. 上传新附件。
5. 停用附件。
6. 新增外链。
7. 停用外链。
8. 新增视频标注。
9. 停用视频标注。
10. 审批通过。
11. 退回发起人。
12. 发起人撤销。
13. 三级驳回。
14. 系统判定持证并自动跳过一级审批。

## 十三、配置与系统集成

### （一）租户范围

审批链映射与媒体/栏目预设按租户隔离，不同租户互不影响。

### （二）审批链映射

系统需维护“流程类型 -> 一级审批角色 -> 二级审批角色 -> 三级审批角色”的映射关系。

配置规则如下：

1. 审批角色成员继续复用现有角色管理。
2. 流程到审批角色的映射复用现有轻量配置能力。
3. 角色引用使用 `roleKey`，不使用数据库主键作为业务配置依据。

### （三）持证发起人角色

1. 系统使用一个通用的“持证发起人”专用角色表达持证资格。
2. 审核流程与校对流程共用该角色。
3. 提交或再次提交时实时判定该角色。

### （四）媒体/栏目预设

1. 媒体/栏目预设复用现有字典或轻量配置能力。
2. 前台支持从预设中选择，也允许手工补录。
3. 手工补录值不自动写回全局预设。

### （五）缺配置拦截

以下情况必须在发起或再次提交前直接拦截：

1. 某流程类型未配置完整审批链映射。
2. 审批链映射存在，但某一级审批角色没有有效成员。

系统应给出明确提示，说明缺失的是哪一级审批角色或哪类配置。

## 十四、验收标准

一期验收至少覆盖以下业务场景：

1. 普通发起人新增并提交流程，完整通过一级、二级、三级审批后完成。
2. 持证发起人新增并提交流程，自动跳过一级审批，直接进入二级审批。
3. 持证发起人被退回后修改保存，再次提交时再次自动跳过一级审批。
4. 任意审批节点退回发起人后，发起人可修改并再次提交。
5. 审批人在其待办阶段可修改流程资料，再进入待办办理审批。
6. 发起人在审批中可撤销流程。
7. 三级审批可驳回并终止当前流程。
8. 一条流程包含多个视频时，详情页可切换视频并播放。
9. 视频时间点和时间段标注可正常新增、跳转、停用。
10. 非法时间输入、时间越界、结束时间早于开始时间时，系统能正确拦截。
11. 当前资源列表仅展示有效资源，历史时间线仍可追溯停用资源。
12. 列表与详情中的所有展示内容均为业务可读文案，不裸露 id、账号或技术码值。

## 十五、后续扩展方向

以下内容作为后续扩展方向保留，不纳入一期承诺：

1. 草稿能力。
2. 删除与回收站能力。
3. 会签、并行、转办、认领等复杂审批形态。
4. Office 文档在线预览。
5. 对接稿件主数据与媒体主数据系统。
6. 更细粒度的持证资格档案管理，例如证书编号、证书类型、有效期等。

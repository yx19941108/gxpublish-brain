## 4. 执行原则

### 4.1 证据层

每次验收至少按以下 3 层取证：

1. 浏览器层：
   - 页面显示
   - 按钮显隐
   - 跳转行为
   - 预览行为
2. 接口层：
   - 请求 URL
   - 请求方法
   - 响应状态
   - 关键响应字段
3. 数据层：
   - 主表状态
   - history 留痕
   - 资源状态
   - 权限 / 菜单 / 角色绑定

### 4.2 分轮执行要求

1. 每轮修复后，必须先执行对应轮次用例 + 本文定义的“本轮最小存量回归”
2. 所有轮次修复完成后，必须执行本文定义的“全量总验收”
3. 不允许只测修复点，不测被带坏的相邻能力

### 4.3 问题 3 / 7 专项提醒

1. 问题 3 必须按“发起人来源 ∪ 审批人来源 ∪ 历史参与人来源”验收
2. 问题 7 必须按“每条 history 均有操作人 + 主句完整表达”验收
3. 这两项是强绑定关系，不允许拆开判通过

## 7. 详细测试用例

### 7.1 问题 1：暂存删除误走全局 OSS 删除权限

#### TC-01 暂存删除改走模块内接口

- 测试目标：确认新增页 / 修改页的暂存删除不再直接调用全局 `/resource/oss/{ossId}`。
- 前置条件：当前用户具备表单访问权限；页面上存在至少一个暂存上传资源。
- 操作步骤：
  1. 进入新增页或修改页。
  2. 上传一个暂存资源。
  3. 点击该资源的删除。
- 预期结果：
  1. 前端调用 manuscript-review 模块内暂存删除接口。
  2. 不再直接调用全局 OSS 删除接口。
  3. 页面删除成功，无“没有权限”报错。

#### TC-02 无全局 OSS 删除权限用户仍可删暂存资源

- 测试目标：确认该能力不再依赖 `system:oss:remove`。
- 前置条件：测试用户不具备全局 OSS 删除权限，但具备本模块合法表单权限。
- 操作步骤：
  1. 上传暂存资源。
  2. 执行删除。
- 预期结果：
  1. 删除成功。
  2. 资源从暂存区消失。
  3. 不要求给用户补全局 OSS 删除权限。

### 7.2 问题 2：视频预览 / 播放时进度条不动

#### TC-03 失败样本三元证据补取

- 测试目标：确认问题 2 的判定证据可被完整提取。
- 前置条件：游工提供失败样本或复现样本。
- 操作步骤：
  1. 记录失败样本 `reviewId`。
  2. 打开详情接口响应，记录 `videoList.resourceUrl`。
  3. 查对应 `sys_oss` 行的 `service / file_name / url`。
- 预期结果：
  1. 三元证据完整。
  2. 可以据此判断失败点属于地址、Range 能力还是前端源切换问题。

#### TC-04 基准样本最小复核

- 测试目标：确认当前基准样本是否仍无法复现。
- 前置条件：样本 `reviewId=2038409700130729985` 仍可访问。
- 操作步骤：
  1. 打开详情页视频。
  2. 开始播放。
  3. 观察网络请求与播放进度。
- 预期结果：
  1. 请求命中视频资源。
  2. 若是同域预览方案，能见到 `206 Partial Content`。
  3. `currentTime` 正常前进。
  4. 若仍无法复现，问题 2 保持补证状态，不扩成修复结论。

### 7.3 问题 3：审校台账分页与数据源口径不一致

#### TC-05 台账改为数据库分页

- 测试目标：确认台账不再是“全量查内存再分页”。
- 前置条件：列表存在多条记录。
- 操作步骤：
  1. 调用台账接口，带 `pageNum/pageSize`。
  2. 查看后端实现与接口返回。
- 预期结果：
  1. 返回结果符合分页语义。
  2. 不再通过 Java 内存 `subList` 完成分页。
  3. 数据库层完成筛选、去重、排序、分页。

#### TC-06 发起人角色只看到自己发起的

- 测试目标：确认发起人来源口径正确。
- 前置条件：准备当前用户发起与其他用户发起的多条样本。
- 操作步骤：
  1. 用仅具发起人角色的账号进入台账。
- 预期结果：
  1. 只能看到 `initiator_user_id = 当前用户` 的记录。
  2. 不会因为当前是审批节点命中或其他人办理历史而额外看到无关记录。

#### TC-07 审批人角色按 `current_node_status` 集合看到当前可审记录

- 测试目标：确认审批人来源口径正确。
- 前置条件：准备 `LEVEL_1 / LEVEL_2 / LEVEL_3` 三类当前待审样本。
- 操作步骤：
  1. 用一级审批人登录查看台账。
  2. 用二级审批人登录查看台账。
  3. 用三级审批人登录查看台账。
- 预期结果：
  1. 一级审批人能看到 `LEVEL_1` 样本。
  2. 二级审批人能看到 `LEVEL_2` 样本。
  3. 三级审批人能看到 `LEVEL_3` 样本。
  4. 不依赖“先查待办/已办再回主表”的旧模式。

#### TC-08 多审批角色用户看到审批状态并集

- 测试目标：确认多审批角色时状态集合取并集。
- 前置条件：存在同时具有多个审批角色的用户。
- 操作步骤：
  1. 使用同时具备多审批角色的用户打开台账。
- 预期结果：
  1. 可见记录覆盖其所有审批角色对应的状态集合。
  2. 不重复展示同一主单。

#### TC-09 历史参与人兜底可见

- 测试目标：确认历史参与人来源独立生效。
- 前置条件：准备一条当前用户曾办理过、但当前已不在其发起/审批角色视角内的样本。
- 操作步骤：
  1. 用该用户查看台账。
- 预期结果：
  1. 该样本仍可见。
  2. 可见性来自 `history.actor_user_id = 当前用户` 兜底。

#### TC-10 发起人来源、审批人来源、历史参与人来源取并集且去重

- 测试目标：确认问题 3 的最终并集口径整体正确。
- 前置条件：同一用户同时命中 3 类来源中的 2 类或 3 类。
- 操作步骤：
  1. 用该用户查询台账。
- 预期结果：
  1. 结果是 3 类来源的并集。
  2. 同一主单只出现一次。
  3. 排序与分页稳定。

### 7.4 问题 4：PDF 预览 access denied

- 预期结果：
  1. 请求命中 manuscript-review 模块内预览接口或其代理地址。
  2. 响应适合浏览器 inline 预览。
  3. 不再把 OSS 私有地址直接暴露给前端。

  2. 当前审批人具备 edit / goApprove。
  3. 被退回发起人具备 edit / resubmit。

# R6.31_WP6-G1多Agent修复提示词

## 0. 文档定位

- 本文不是新方案，也不是架构重审。
- 本文只服务于当前已确认的 `WP6-G1` 后端验收失败项修复：
  1. 持证场景 `CREATE / SKIP_LEVEL_1` 顺序错误
  2. `current_node_label` 与冻结文案脱节，进而打坏 detail / update / back / resubmit
- 本文给出：
  - 是否适合开多 agent
  - 最多开几个 agent 才有净收益
  - 每个 agent 的 owned files / 输出物 / 量化收益
  - 可直接用于新会话或外部 Codex CLI 的提示词

## 1. 是否适合开多 Agent

### 1.1 结论

- `适合开多 agent`
- 但只适合 `1 个 backend 主修 agent + 1 个 frontend/影响面 sidecar agent`
- `不适合` 开成 2 个并行 backend agent

### 1.2 原因

这两个问题的 backend 写集高度重叠，核心重叠文件至少包括：

- `Brain/brain-modules/brain-manuscript-review/src/main/java/.../service/ManuscriptReviewService.java`
- `Brain/brain-modules/brain-manuscript-review/src/main/java/.../service/ManuscriptReviewReadableService.java`
- `Brain/brain-modules/brain-manuscript-review/src/main/java/.../domain/entity/ManuscriptReviewRecordEntity.java`
- `Brain/brain-modules/brain-manuscript-review/src/main/java/.../domain/entity/ManuscriptReviewHistoryEntity.java`
- `Brain/brain-modules/brain-manuscript-review/src/test/java/.../ManuscriptReviewServiceTest.java`
- `Brain/script/sql/update/*manuscript_review*`

如果把两个 backend 问题拆给两个 agent 并行改：

- 冲突概率高
- 集成成本高
- 反而容易把 `sorted / current_node_status / current_node_label` 三条线改散

因此当前最优解不是“多 backend 并行”，而是：

1. `Backend 主修 agent`
  - 负责 schema + enum + service/readable + backend tests
2. `Frontend sidecar agent`
  - 只负责评估并吸收 `currentNodeStatus/currentNodeLabel` 对 manuscript-review 前端的影响
  - 如果 shared 响应保持兼容，可给出 `NO_CHANGE + 证据`

## 2. 量化方案

### 2.1 推荐并发模型

| 角色 | 是否推荐 | 工作量占比 | 主要收益 | 风险 |
|------|----------|-----------|---------|------|
| Controller / 主控 | 必须 | 15% | 冻结 shared 串行区、整合结果、最终 rerun | 若主控放任并行改 shared，冲突概率极高 |
| Backend 主修 agent | 必须 | 65% | 直接消除 gate blocker | 写集最集中，必须单 owner |
| Frontend sidecar agent | 推荐 | 20% | 并行评估前端影响并做最小适配或给出 NO_CHANGE | 若过早依赖未冻结 shared 字段，会返工 |

### 2.2 净收益评估

| 维度 | 评分 | 说明 |
|------|------|------|
| context 更干净 | 7/10 | backend 与 frontend 影响面天然分层 |
| context-loss / corruption 风险更低 | 6/10 | 前提是 backend 只能有 1 个 owner |
| 任务规模足够大 | 7/10 | 涉及 SQL、实体、枚举、服务、读侧、测试、前端适配判定 |
| 扣除集成成本后的净效率 | 6/10 | `2 agent` 有净收益；`3+ agent` 开始负收益 |
| 独立评审 / 并行价值 | 8/10 | frontend sidecar 可以提前发现 contract breakage |

### 2.3 预计耗时

| 包 | 单线程估算 | 推荐 2-agent 估算 | 节省 |
|----|-----------|------------------|------|
| backend schema + logic + tests | 70-100 分钟 | 70-100 分钟 | 0，仍是关键路径 |
| frontend impact scan + patch / no-change proof | 25-45 分钟 | 20-35 分钟并行 | 20-35 分钟 |
| controller 集成 + rerun + 落盘 | 20-30 分钟 | 20-30 分钟 | 0 |
| 总计 | 115-175 分钟 | 90-130 分钟 | 约 20%-25% |

结论：

- `2 agent` 有意义
- `>2 agent` 不推荐

## 3. 串行 / 并行边界

### 3.1 必须串行的 shared 区

以下内容只允许一个 owner 改，建议由 backend 主修 agent 统一负责，controller 最终 review：

- 新增 SQL 升级脚本：
  - `Brain/script/sql/update/20260326_manuscript_review_node_status_sorted_fix_v01.sql`
  - 名称可微调，但只允许一份主脚本
- `current_node_status` 字段定义
- `sorted` 字段定义
- Java 实体字段名
- `ManuscriptReviewNodeStatusEnum` 命名与值
- `currentNodeLabel/currentNodeStatus` 的最终映射规则

### 3.2 适合并行的 private 区

#### Backend 主修 agent

owned files:

- `Brain/script/sql/update/*manuscript_review*`
- `Brain/brain-modules/brain-manuscript-review/src/main/java/com/gxpublish/brain/manuscript/review/domain/entity/**`
- `Brain/brain-modules/brain-manuscript-review/src/main/java/com/gxpublish/brain/manuscript/review/domain/enums/**`
- `Brain/brain-modules/brain-manuscript-review/src/main/java/com/gxpublish/brain/manuscript/review/service/**`
- `Brain/brain-modules/brain-manuscript-review/src/test/java/com/gxpublish/brain/manuscript/review/service/**`
- 如有必要：
  - `.../controller/response/**`
  - `.../controller/request/**`

deliverable:

- schema 升级脚本
- backend 代码修复
- backend 定向测试补齐
- 说明哪些 runtime blocker 被预期消除

#### Frontend sidecar agent

owned files:

- `plus-ui-ts/src/api/manuscript-review/types.ts`
- `plus-ui-ts/src/views/manuscript-review/detail.contract.ts`
- `plus-ui-ts/src/views/manuscript-review/detail.vue`
- `plus-ui-ts/src/views/manuscript-review/index.vue`
- `plus-ui-ts/src/views/manuscript-review/*.spec.ts`

deliverable:

- 若需要：最小前端适配 patch
- 若不需要：`NO_CHANGE + 影响面扫描结论`
- 明确哪些页面只消费 `currentNodeLabel`，哪些地方若引入 `currentNodeStatus` 需同步

## 4. 本轮修复硬约束

1. 不参考旧失败实现。
2. `brain-manuscript-review` 只作为代码落点，不作为实现基线。
3. 不以现存代码反推冻结契约。
4. 修复目标只限：
  - `sorted`
  - `current_node_status`
  - `currentNodeLabel/currentNodeStatus` 一致性
  - 由此导致的 detail / update / back / resubmit blocker
5. 不顺手扩成新的 shared 包、治理包、R7 包。
6. 仍以 `R6.26 / R6.27 / R6.28 / R6.30` 为裁决源。

## 5. 建议执行顺序

1. Controller 先发包，冻结边界。
2. Backend 主修 agent 开工。
3. Frontend sidecar agent 并行扫描 impact，等待 backend shared 字段落点。
4. Backend 提交后，Frontend 决定：
  - patch
  - 或 `NO_CHANGE`
5. Controller 本地集成。
6. Controller 重新跑：
  - fresh HTTP
  - SQL
  - BPM
  - JDK17 定向测试
7. 结果落盘到新的 `doc/manuscript_review/R6.3x_*.md`

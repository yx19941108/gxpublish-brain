# R8.4.6_问题3台账口径冻结

## 1. 文档定位

本文用于冻结 `manuscript_review / 问题 3：审校台账分页与数据源口径不一致` 的最新业务口径。

本文不是新的实现方案比较文档，而是对前述讨论的最终收口。自本文起，问题 3 的业务口径以本文为准；若与 `R8.2 / R8.3 / R8.2.5 / R8.4.5` 中旧口径冲突，以本文为准。

## 2. 为什么要冻结

已确认当前出现了新的业务事实：

1. 新创建的用户不应该看到历史流程数据
2. 当前 BPM 的“我的待办 / 我的已办”本身也不采用“历史参与人兜底可见”口径
3. 因此，问题 3 不能继续沿用“发起人来源 ∪ 审批人来源 ∪ 历史参与人来源”的口径

## 3. 最终业务口径

### 3.1 发起人

1. 菜单：
   - `台账`
   - `我发起的`
2. 台账创建：
   - 可创建
3. 台账可见范围：
   - `我发起的`
4. 台账可操作范围：
   - 不具备审批操作
   - 是否允许修改，仅取决于该单据是否处于发起人可编辑态

### 3.2 审批人

1. 菜单：
   - `台账`
   - `我的待办`
   - `我的已办`
2. 台账创建：
   - 不可创建
3. 台账可见范围：
   - `我的待办 ∪ 我的已办`
4. 台账可操作范围：
   - 仅 `我的待办` 可 `去审批 / 修改`
   - `我的已办` 仅可查看，不因可见而获得审批操作

### 3.3 发起人混合审批人

1. 菜单：
   - `台账`
   - `我发起的`
   - `我的待办`
   - `我的已办`
2. 台账创建：
   - 可创建
3. 台账可见范围：
   - `我发起的 ∪ 我的待办 ∪ 我的已办`
4. 台账可操作范围：
   - 仅 `我的待办` 可 `去审批 / 修改`
   - `我发起的` 与 `我的已办` 不因可见而获得审批操作

## 4. 与旧口径的冲突处理

以下旧口径自本文起废弃：

1. `历史参与人兜底可见`
2. “发起人来源 ∪ 审批人来源 ∪ 历史参与人来源”作为问题 3 的最终并集口径
3. 任何基于 `history.actor_user_id` 扩大台账可见性的实现或验收结论

## 5. 实现约束

问题 3 后续实现时，必须同时区分：

1. 台账可见性
2. 台账行级操作权限
3. 台账页“新增”按钮显隐

明确要求：

1. 不能只改 `listLedger`
2. 不能让“可见”自动等于“可操作”
3. 不能因为用户混合拥有发起人与审批角色，就对“我发起的 / 我的已办”错误展示 `去审批 / 修改`

## 6. 推荐实现方向

本文只冻结业务口径，不强制具体代码写法。

但在当前已确认口径下，更符合业务的实现方向是：

1. 后端先基于三类权威来源求可见 `businessId/reviewId`
   - 我发起的
   - 我的待办
   - 我的已办
2. 再以该集合回主表做数据库级筛选、排序、分页
3. 行级操作权限单独计算，仅对“我的待办”开放审批型动作

## 7. 对后续文档与验收的影响

后续修复问题 3 时，需要同步修订：

1. `R8.2` 中问题 3 的方案表述
2. `R8.3` 中问题 3 的冻结口径
3. `R8.2.5` 中问题 3 的测试用例
4. `R8.4.5` 中基于旧口径写出的运行态结论

## 8. 禁止事项

1. 不得继续把 `history.actor_user_id` 当作问题 3 的默认兜底可见来源
2. 不得把“新用户不看旧历史”与“历史参与人兜底可见”混写
3. 不得只改台账列表 SQL，而不改行级操作权限与按钮显隐

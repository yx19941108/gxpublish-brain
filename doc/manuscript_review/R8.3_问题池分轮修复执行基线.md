## 4. 歧义清除

### 4.1 问题 3 的最终口径

问题 3 不再使用 `R8.2` 中容易误解的旧伪代码。
最终执行口径固定为“3 类可见性来源做并集”：

1. 发起人来源：
   - 若当前用户拥有发起人角色，则可见 `initiator_user_id = 当前用户` 的记录
2. 审批人来源：
   - 若当前用户拥有审批人角色，则根据其审批角色映射的 `current_node_status` 集合查询
   - 例如一级审批人命中 `LEVEL_1`，二级审批人命中 `LEVEL_2`，三级审批人命中 `LEVEL_3`
   - 若同时拥有多个审批角色，则审批状态集合取并集
3. 历史参与人来源：
   - 无论当前角色怎样变化，只要 `brain_manuscript_review_history.actor_user_id = 当前用户`，该记录仍应可见

最终列表可见性 = 上述 3 类来源的并集，再对主表去重、排序、分页。

明确禁止以下误读：

1. 不得再理解成“先从我发起 / 待办 / 已办三套页面查 `businessId`，再回主表分页”
2. 不得再理解成“审批人来源必须同时满足 `当前审批节点 AND 历史办理过` 才可见”
3. 不得把 `create_by` 当成发起人唯一口径；发起人口径优先用业务字段 `initiator_user_id`
4. 不得回退到 Java 内存分页；必须在数据库内完成筛选、去重、排序、分页

### 4.2 问题 7 的最终口径

问题 7 的最终口径固定为：

1. 每条 history 记录都必须有操作人
2. `actor_user_id` 与 `actor_user_name` 不能再作为“系统动作可为空”的宽松字段来使用
3. workflow 回写出来的业务历史也属于“由真人操作触发的业务副作用”，因此同样必须能追溯到操作人
4. 时间线主文案必须能表达“谁在什么环节做了什么”

明确禁止以下做法：

1. 继续保留“流程已退回发起人处理”这类无操作人的裸文案
2. 继续把主语义拆成“第一行事件 + 第二行姓名”来凑完整含义
3. 只补 `action_text`，不补 `actor_user_id / actor_user_name`

### 4.3 问题 9 的最终口径

问题 9 的目标不是只做前端显隐，而是三层同时收紧：

1. 菜单 / 路由入口
2. controller 接口权限
3. service 业务二次校验

只改其中一层，视为未完成。

## 5. 分轮修复定义

## 5.1 第一轮：权限与台账语义收口轮

### 本轮目标问题

1. 问题 9：新增权限未收紧
2. 问题 3：审校台账分页与数据源口径不一致
3. 问题 7：history 主文案不完整

### 本轮目标

1. 先把越权发起风险关掉
2. 先把台账可见性和分页口径改成数据库内真实口径
3. 先把 history 的“谁做了什么”与 `actor_user_id / actor_user_name` 基础打牢

### 本轮不做

1. 不进入问题 1
2. 不进入问题 5 / 6
3. 不进入问题 8 的预览架构改造
4. 不把问题 2 扩成代码修复

### 本轮实现要求

1. 问题 9：
   - 发起人角色可新增
   - 审批人角色不可新增
   - 共享 `/manuscript/review/form?mode=create` 入口必须收紧
   - 后端提交入口必须受权限拦截
2. 问题 3：
   - 新台账查询按“发起人来源 ∪ 审批人来源 ∪ 历史参与人来源”实现
   - 数据库内去重、排序、分页
   - 不再依赖“我发起的 / 我的待办 / 我的已办”页面先查一遍再回主表
3. 问题 7：
   - 新写入的 history 必须带 `actor_user_id / actor_user_name`
   - 主文案必须完整表达“谁在什么环节做了什么”
   - 至少覆盖提交、再次提交、修改、通过、退回、驳回、资源动作、标注动作

### 本轮 gate

只有同时满足以下条件，才允许进入第二轮：

1. 审批人角色无法从前端或直接接口越权发起新增
2. 台账查询已改为数据库分页，不再是 Java 内存分页
3. 同一用户同时具备多角色时，台账结果符合并集口径
4. history 新记录全部带 `actor_user_id / actor_user_name`
5. 时间线主文案不再依赖第二行姓名补语义

## 5. 本轮固定口径

### 5.1 问题 3 固定口径

1. 发起人来源：若当前用户拥有发起人角色，则可见 `initiator_user_id = 当前用户` 的记录
2. 审批人来源：若当前用户拥有审批人角色，则按其审批角色映射出的 `current_node_status` 集合查询
3. 历史参与人来源：只要 `brain_manuscript_review_history.actor_user_id = 当前用户`，该记录仍应可见
4. 最终列表 = 上述三类来源并集，再对主表去重、排序、分页
5. 禁止回到 Java 内存分页
6. 禁止再做“先从我发起/待办/已办查 businessId，再回主表分页”

### 5.2 问题 7 固定口径

1. 每条 history 都必须有操作人
2. `actor_user_id / actor_user_name` 必须补齐
3. workflow 触发的业务副作用 history 也必须能追溯到真人
4. 主文案必须直接表达“谁在什么环节做了什么”
5. 禁止继续保留“流程已退回发起人处理”这类无操作人的裸文案

### 5.3 问题 9 固定口径

1. 菜单/路由入口收紧
2. controller 接口权限收紧
3. service 业务二次校验收紧
4. 只改一层视为未完成

## 6. 并行结论

当前不建议多开并行 implementer subagent。

量化结论：

1. 上下文更干净：`3/5`
2. 语义耦合可拆分度：`2/5`
3. 写集冲突风险可控度：`1/5`
4. 净效率收益：`2/5`
5. 独立复核价值：`4/5`

综合：`12/25 = 48/100`

原因：

1. 问题 3 / 7 / 9 都会撞到 `ManuscriptReviewService.java`
2. 问题 3 与 7 必须同轮同文件域收口
3. 问题 9 的 service 二次校验也在同一核心服务

允许的最宽并行方式：

1. 不开 implementer subagent，主控本地执行
2. 若必须并行，最多允许 1 个短生命周期 worker 处理“前端入口 + 菜单 SQL”边界，后端核心与集成回归仍由主控收口

默认建议：下一轮不开 implementer subagent，直接本地修复。

## 8. 续工追加：根因定位

在本文件上述失败记录基础上，后续已直接按 `GET /workflow/manuscript-review/list` 真链路下钻，并拿到以下确定性结论。

### 8.1 前端与接口响应体

前端台账页实际仍命中：

1. `GET /workflow/manuscript-review/list`

续工时补取到的真实响应体：

1. `mr_approver_l1 + keyword=MR-I3-L1-`：
   - 返回 `total=0, rows=[]`
2. `mr_mix_l1 + keyword=MR-I3-MIX-`：
   - 返回 `total=1`
   - 仅返回 `MR-I3-MIX-INIT-001`

这说明浏览器失败不是“页面没渲染出来”，而是接口返回本身就缺审批侧样本。

### 8.2 controller / service / mapper 真链路

实际命中链路为：

1. `ManuscriptReviewReadableApiController.list`
2. `ManuscriptReviewReadableService.listLedger`
3. `ManuscriptReviewRecordMapper.customSelectVisibleLedgerPage`

其中 service 侧已按冻结口径做并集：

1. `我发起的`
2. `我的待办`
3. `我的已办`

也就是说，问题不在 controller/service 的并集思路，而在 mapper SQL 获取审批侧来源时被错误过滤。

### 8.3 数据库与 SQL 根因

数据库直查已确认：

1. 问题 3 的待办/已办样本真实挂在 `flow_definition.flow_code = manuscript_review_audit_flow`
2. `MR-I3-L1-WAIT-001 / MR-I3-MIX-WAIT-001` 在待办表里可被对应审批人命中
3. `MR-I3-L1-FIN-001 / MR-I3-MIX-FIN-001` 在已办表里可被对应审批人命中

但当时 mapper 中两条审批侧来源 SQL 写成了：

1. `d.flow_code = 'manuscript_review_'`

该条件与真实 `flow_code` 不匹配，直接导致：

1. `selectWaitingBusinessIds(...)` 返回空
2. `selectFinishedBusinessIds(...)` 返回空
3. 纯审批人只能看到空列表
4. 混合角色只能退化成“只看我发起的”

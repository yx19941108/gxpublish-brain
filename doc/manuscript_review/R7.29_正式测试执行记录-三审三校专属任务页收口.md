## 3. 为什么放弃改通用 workflow 任务页

放弃继续改通用 workflow 任务页，原因已经足够明确：

1. 第二队列待收口问题本质上都属于 manuscript-review 专属业务规则，不适合继续压在通用任务页里做特判
2. `用例-41 / 58` 依赖 manuscript-review 自身撤销接口、退回后编辑路由与历史留痕，不应继续走通用工作流接口与通用跳转
3. `用例-46 / 47 / 48` 依赖 manuscript-review 流程节点按钮与驳回目标约束，本质应由 manuscript_review 目录下 SQL 与业务页承接
4. 通用 workflow 页继续承载 manuscript-review 特判，会同时放大：
   - 共享页面耦合风险
   - 回归面
   - 回滚成本
   - 与上游 `RuoYi-Vue-Plus` 通用行为的偏离
5. 改为专属页面后，路由、菜单、按钮规则、返回链路和 SQL 归属都能收敛到 manuscript-review 自己的边界内，更利于验证和回滚

## 4. 为什么改为三审三校专属任务页

改为三审三校专属任务页的收益主要有：

1. 入口边界清晰：
   - 角色菜单直接进入 manuscript-review 自己的 `我发起 / 我的待办 / 我的已办`
2. 行为边界清晰：
   - 发起人撤销直接走审校业务接口
   - 退回态编辑直接回到审校业务编辑页
   - 审批办理成功后直接返回专属待办页
3. 配置边界清晰：
   - 审批按钮集合与驳回目标通过 manuscript_review 目录下 SQL 管理
4. 验证边界清晰：
   - 不需要再把 manuscript-review 的页面行为与通用 workflow 页面行为混在同一套预期里解释

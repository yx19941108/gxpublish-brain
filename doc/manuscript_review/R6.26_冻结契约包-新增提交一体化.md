## 2. 本轮完整冻结口径

### 2.1 新增并提交是一个业务动作

新增页的“提交”不是“先保存主单，再单独发起流程”两个业务动作。

对用户来说，它就是一次操作：
- 填主表
- 上传附件 / 视频或填写外链
- 点击提交
- 后端在一个事务里完成：校验、写资源、生成稿件号、写主表、写 history、发 BPM

因此，本轮冻结后：
- 新增页不再以“新增保存”作为正式业务动作。
- 新增页的正式业务动作只有“提交”。
- 新增提交时，不应再出现 `CREATE -> RESOURCE_ADD -> SUBMIT` 这种把一个动作拆成多个业务动作的口径。

### 2.2 修改保存也是一个业务动作，但不推进流程

修改页的“保存”与新增页一样，也按“一次性提交整个表单”处理：
- 主表字段一起提交
- 资源参数一起提交
- 资源参数只提交“这次新追加的附件 / 外链”

后端在一次保存里完成：
- 校验参数
- 保存主表
- 保存这次追加的资源
- 写保存历史

但修改保存和新增提交有一个关键区别：
- **修改保存不做流程状态变更**
- **修改保存不提交 BPM**

流程动作依然后置到：
- 去审批
- 重新提交

### 2.3 资源的三种状态必须分开理解

#### 第一种：未提交前的上传暂存资源
- 只存在于前端表单和文件服务里
- 还不是正式业务资源
- 删除时走 `DELETE /resource/oss/{ossId}`
- 不写业务表
- 不写业务 history

#### 第二种：新增提交时一并带上的正式资源
- 由后端在“新增并提交”的事务里落到业务资源表
- 属于该流程单正式资源
- 与主表、history、BPM 一起收敛

#### 第三种：修改保存时一并追加的正式资源
- 由后端在“修改保存”的事务里落到业务资源表
- 只允许提交“新增追加”的资源参数
- 不在保存时推进流程

### 2.4 仍然有效的旧冻结内容

以下内容仍然有效，应合并保留：
- 列表页只承担搜索、筛选、状态查看、进详情
- 详情页是动作中枢：看状态、看资源、看历史、做按钮分流
- `permissionMatrix` 仍是详情页按钮分流的唯一后端来源
- 发起人撤销仍是独立流程动作
- 重新提交仍是独立流程动作
- 已入库资源的停用仍是独立动作
- 视频标注的新增 / 停用仍保留独立业务能力
- 审批通过后的 `APPROVE` history 继续保留，且文案要业务可读

## 3. history 与 BPM 冻结规则

### 3.1 新增并提交：非持证发起人
- 只产生 1 条业务 history：`CREATE`
- 不额外产生 `SUBMIT`
- 不额外产生 `RESOURCE_ADD`
- BPM 真实进入一级审批节点

### 3.2 新增并提交：持证发起人
- 只产生 2 条业务 history：
  1. `CREATE`
  2. `SKIP_LEVEL_1`
- 不额外产生 `SUBMIT`
- 不额外产生 `RESOURCE_ADD`
- BPM 不产生一级审批待办
- BPM 真实进入二级审批节点

### 3.3 持证发起人的 history 顺序
- 顺序必须固定为：`CREATE -> SKIP_LEVEL_1`
- 不能先跳级再看到新增
- 当前若只靠 `create_time` 不能稳定保证顺序，应明确记为缺口

### 3.4 修改保存
- 修改保存至少要产生 1 条 `UPDATE`
- 这条 `UPDATE` 表示“本次保存动作已经完成”
- 修改保存阶段不产生 `APPROVE`
- 修改保存阶段不改变 BPM 当前节点

### 3.5 审批通过
- 一级审批通过后，必须产生 1 条 `APPROVE`
- 二级审批通过后，必须再产生 1 条 `APPROVE`
- `actionText` 必须一眼能看明白：哪一级通过了，审批意见是什么

## 4. 三条完整流程

## 4.1 用户新增流程

### 流程说明
- 这是“新增并提交”的完整业务主路径。
- 目标是把新增页的一次提交动作，直接收敛成正式业务主单 + 正式资源 + 正式 history + 正式 BPM 发起。

### 页面：新增页
操作：上传附件 / 视频
调用接口：现有上传接口
参数：文件本体
后端做什么：只保存文件并返回上传结果，不写业务表
返回什么：至少返回 `ossId` 或等价上传结果
前端拿到结果后怎么处理：把上传结果暂存在新增表单里，供最后提交时一起带给后端

### 页面：新增页
操作：删除未提交的已上传附件
调用接口：`DELETE /resource/oss/{ossId}`
参数：`ossId`
后端做什么：删除文件服务中的暂存文件
返回什么：删除结果
前端拿到结果后怎么处理：从新增表单中删除该附件参数；这一步不写业务 history

### 页面：新增页
操作：填写主表 + 外链 + 当前仍有效的附件参数后点击提交
调用接口：`POST /workflow/manuscript-review/submitAndFlowStart`
参数：
- 主表字段：`processType`、`externalManuscriptCode`、`title`、`mediaChannel`、`submitDepartment`、`authorName`、`remark`、`contentBody`
- 附件参数：当前仍有效的上传结果列表
- 外链参数：当前填写的外链列表
后端做什么：
1. 校验主表字段
2. 校验附件参数和外链参数是否全空
3. 校验上传结果是否合法
4. 写附件表 / 链接表
5. 生成 `manuscriptCode`
6. 写主表
7. 写 history
8. 发 BPM
返回什么：提交流程后的详情结果，或等价成功结果
前端拿到结果后怎么处理：
- 成功：跳转详情页
- 失败：留在新增页并按后端错误提示修正

### 新增流程的结果判定
- 非持证：只看到 `CREATE`，BPM 到一级审批
- 持证：看到 `CREATE -> SKIP_LEVEL_1`，BPM 到二级审批

## 4.2 用户修改并审批流程

### 流程说明
- 适用于“当前有修改权的人先改表单，再去 BPM 页面做审批”。
- 这里要明确：修改保存和审批是两个业务动作，不允许把二者混成一个按钮结果。

### 页面：详情页
操作：点击“修改”
调用接口：无新增接口，前端跳转到修改页
参数：当前流程单 `id`
后端做什么：无新增动作
返回什么：无
前端拿到结果后怎么处理：跳转修改页并加载详情数据

### 页面：修改页
操作：加载待修改表单
调用接口：`GET /workflow/manuscript-review/{id}`
参数：`id`
后端做什么：返回主表、当前有效资源、历史、权限矩阵等详情
返回什么：详情对象
前端拿到结果后怎么处理：回填表单，显示已入库资源，并允许追加新资源参数

### 页面：修改页
操作：上传新的附件 / 视频
调用接口：现有上传接口
参数：文件本体
后端做什么：只保存文件并返回上传结果，不写业务表
返回什么：至少返回 `ossId` 或等价上传结果
前端拿到结果后怎么处理：把上传结果暂存在修改表单里，等待保存时一并提交

### 页面：修改页
操作：删除本次新上传但尚未保存的附件
调用接口：`DELETE /resource/oss/{ossId}`
参数：`ossId`
后端做什么：删除暂存文件
返回什么：删除结果
前端拿到结果后怎么处理：从本次追加资源参数里删除该项

### 页面：修改页
操作：点击保存
调用接口：`PUT /workflow/manuscript-review`
参数：
- 主表字段：`id`、`processType`、`externalManuscriptCode`、`title`、`mediaChannel`、`submitDepartment`、`authorName`、`remark`、`contentBody`
- 资源参数：本次新追加的附件参数、本次新追加的外链参数
后端做什么：
1. 校验主表字段
2. 校验追加资源参数是否合法
3. 保存主表
4. 保存本次追加资源
5. 写 `UPDATE` history
6. 不改 BPM 当前节点
7. 不发 BPM
返回什么：保存后的详情结果，或等价成功结果
前端拿到结果后怎么处理：
- 成功：回到详情页
- 失败：留在修改页并提示修正

### 页面：详情页
操作：点击“去审批”
调用接口：无新增业务接口，前端跳转 BPM 审批页
参数：由详情返回的审批跳转信息决定；若当前 shared 形态没有足够跳转信息，记为缺口
后端做什么：不新增业务写动作
返回什么：无
前端拿到结果后怎么处理：跳转 BPM 审批页，由 BPM 页面完成审批

## 4.3 用户修改并重新提交流程

### 流程说明
- 适用于“发起人被退回后，先修改保存，再重新提交”。
- 这里同样要明确：修改保存和重新提交是两个业务动作。

### 页面：详情页
操作：点击“修改”
调用接口：无新增接口，前端跳转修改页
参数：当前流程单 `id`
后端做什么：无新增动作
返回什么：无
前端拿到结果后怎么处理：跳转修改页

### 页面：修改页
操作：加载、追加资源、删除未保存新资源、点击保存
调用接口：同“用户修改并审批流程”中的 `GET /{id}`、上传接口、`DELETE /resource/oss/{ossId}`、`PUT /workflow/manuscript-review`
参数：同上
后端做什么：同上
返回什么：同上
前端拿到结果后怎么处理：保存成功后回详情页

### 页面：详情页
操作：点击“重新提交”
调用接口：`POST /workflow/manuscript-review/resubmit`
参数：至少包含 `id`
后端做什么：
1. 校验该流程是否处于允许重新提交的状态
2. 重新判定持证 / 非持证
3. 推进 BPM
4. 写重新提交相关 history
返回什么：重新提交后的详情结果，或等价成功结果
前端拿到结果后怎么处理：
- 成功：刷新详情页
- 失败：继续停留详情页并展示错误提示

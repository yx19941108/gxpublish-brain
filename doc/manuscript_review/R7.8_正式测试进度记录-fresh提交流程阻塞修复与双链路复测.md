# R7.8_正式测试进度记录-fresh提交流程阻塞修复与双链路复测

这份文件用于承接 `R7.6` 之后的新阶段停点，记录：

1. fresh 新增并提交链路为什么在当前轮次被阻塞。

## 2. 本阶段已确认事实

### 2.1 fresh 提交最初为什么失败

起初在真实浏览器里，`mr_initiator` 从新增页点击“提交”后没有进入详情页，而是停在表单页并出现提示：

- `提交失败，请根据提示修正后重试`

为了判断是浏览器脚本问题、前端页面问题还是后端运行态问题，本轮按顺序补了三层证据：

1. 真实浏览器证据：
   - 登录、进新增页、填表、点击提交都成功执行。
   - 失败时页面仍停留在 `/manuscript/review/form?mode=create`。
2. 前端网络证据：
   - `POST /workflow/manuscript-review/submitAndFlowStart` 已真实发出。
3. 后端运行态证据：
   - 旧 `brain-admin.jar` 内部 `ManuscriptReviewApiController.submitAndFlowStart` 的签名仍是：
     - `submitAndFlowStart(ReviewIdRequest)`
   - 但仓库源码已经变成：
     - `submitAndFlowStart(ManuscriptReviewSubmitRequest)`

这说明当时的运行态不是“源码当前版本”，而是“旧 jar + 新前端”的错配态。

### 2.2 旧 jar 错配如何被证实

本轮拿到的直接证据如下：

1. 源码时间晚于旧 jar 时间：
   - `ManuscriptReviewApiController.java`：`2026-03-26 10:29:49`
   - `ManuscriptReviewService.java`：`2026-03-27 10:22:21`
   - `Brain/brain-admin/target/brain-admin.jar`：`2026-03-26 08:55:13`
2. 对旧 jar 做 `javap` 后看到的方法签名仍是旧版：
   - `submitAndFlowStart(com.gxpublish.brain.manuscript.review.controller.ManuscriptReviewApiController$ReviewIdRequest)`
3. 对完整提交体做真实 HTTP 调用时，旧运行态直接返回：
   - `code = 500`
   - `msg = 稿件审校流程不存在`

这个结论意味着：如果不先把运行态追平到源码，后面的正式测试结论都不可信。

### 2.3 运行态追平后，真实代码缺陷是什么

旧 jar 问题排除后，再次对真实 HTTP 做对照验证，发现 fresh 提交还存在第二层真实缺陷：

1. 当前前端 `buildIntegratedSubmitPayload / buildIntegratedSavePayload` 发送的是：
   - `attachmentList`
   - `externalLinkList`
2. 当前后端 `ManuscriptReviewSubmitRequest` 接收的是：
   - `attachmentResources`
   - `externalLinks`

对新 jar 复测后，差异被真实 HTTP 直接验证：

1. 发送前端旧字段名：
   - 返回 `code = 500`
   - 返回 `msg = 稿件至少需要一种有效资源`
2. 发送后端正确字段名：
   - 返回 `code = 200`
   - 返回 `msg = 操作成功`

因此，本阶段 fresh 提交真正的代码缺陷已经明确为：

- 前端提交/保存 payload 字段名与后端冻结契约不一致，导致后端拿不到外链/附件参数，误判为“没有有效资源”。

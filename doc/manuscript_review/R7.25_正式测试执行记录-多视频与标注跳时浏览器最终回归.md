## 3. 问题收敛过程

### 3.1 先前阻塞并非单纯 headless

本轮先复核 `R7.24` 阻塞点，得到：

1. 原详情页播放器直接使用 `resourceUrl = http://127.0.0.1:9000/...mp4`
2. 在当时运行态下，该直链访问结果为：
   - `403 AccessDenied`
3. 浏览器内对应表现为：
   - `readyState = 0`
   - `networkState = 3`
   - `error.code = 4`

结论：

- 原阻塞点不只是“headless 媒体状态异常”，而是**详情页拿到的播放器 URL 不可直接播放**。

### 3.2 下载地址方案不是最终解

本轮一度尝试把播放器切到：

- `/dev-api/resource/oss/download/{ossId}?Authorization=...&clientid=...`

验证结果：

1. 该地址可让播放器进入 metadata
2. 但在真实浏览器中，点击标注后：
   - `currentTime` 在 `30s` 内仍保持 `0`

结论：

- `download` 接口更接近附件下载流，不足以作为最终跳时播放源。

### 3.3 最终根因

本轮最终修复方向改为：

1. 后端详情视频资源改为返回 MinIO 预签名 URL
2. 浏览器实际访问该 URL 时：
   - 真实 `GET Range` 返回 `206 Partial Content`
   - `Content-Type = video/mp4`
   - `Accept-Ranges = bytes`
3. 真实页面播放器状态恢复为：
   - `readyState = 4`
   - `error = null`

结论：

- 多视频与标注跳时的最终闭环依赖的是：
  - **可直接播放且支持 Range 的预签名 OSS URL**
  - 而不是下载接口或 blob 临时注入

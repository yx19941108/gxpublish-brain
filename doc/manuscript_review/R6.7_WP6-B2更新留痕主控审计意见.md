# R6.7_WP6-B2更新留痕主控审计意见

## 0. 审计背景

- 审阅触发问题：
  - 用户明确要求“更新审校表单要留有历史记录”。
  - 当前代码中可看到历史记录查询链，但用户质疑更新动作是否真正写入历史。
- 本次审阅对象：
  - `Brain/brain-modules/brain-manuscript-review/**` 当前代码
  - `Brain/script/sql/update/*manuscript_review*`
  - `doc/manuscript_review/R5.7_第6-7轮执行基线.md`
  - `doc/manuscript_review/R6.5_WP6-shared接缝主控审计结论.md`
  - `doc/manuscript_review/R6.6_WP6-B2完成记录.md`
- 本次硬约束：
  - 不参考旧失败实现
  - 不以现存旧页面/旧 readable 路径反推契约
  - 只判断当前仓库里“历史记录写入链”是否对齐 PRD/R4.5/R5.7 要求

## 1. 审阅结论

- 结论：`不通过`
- 结论边界：
  - 不能写成“历史记录体系不存在”。
  - 也不能写成“更新留痕已闭环”。
- 准确表述应为：
  - `历史表、历史查询链、部分流程动作历史写入已存在`
  - `但更新表单及资源/标注变更未完整写入 history`
  - `当前时间线仍是不完整闭环`

## 2. 已确认

### 2.1 历史表与查询链是存在的

- DDL 已存在：
  - `Brain/script/sql/update/20260321_manuscript_review_ddl_v01.sql`
  - 已建表：`brain_manuscript_review_history`
- 实体与 mapper 已存在：
  - `ManuscriptReviewHistoryEntity`
  - `ManuscriptReviewHistoryMapper`
- 详情查询链已消费历史表：
  - `ManuscriptReviewReadableService` 通过 `historyMapper.selectList(...)` 查询历史
  - 详情响应中已有 `timelineItems`

### 2.2 历史写入不是通过独立 controller API 完成，而是服务内部副作用

- 当前 controller 只暴露：
  - 新增保存
  - 修改保存
  - 提交发起
  - 再次提交
  - 撤销
  - 资源新增
  - 资源停用
  - 视频标注新增
- 当前也不存在视频标注停用的业务 controller 接口。
- 当前并不存在单独的“新增历史记录”外部接口。
- 这本身不是问题；审计历史应由业务服务在真实动作发生时自动写入，而不是让前端单独调 history API 伪造记录。

### 2.3 当前已写入 history 的动作非常有限

- `submitAndFlowStart` 会写：
  - `SUBMIT`
  - 条件命中时再写 `SKIP_LEVEL_1`
- `resubmit` 会写：
  - `RESUBMIT`
  - 条件命中时再写 `SKIP_LEVEL_1`
- `cancelProcessApply` 会写：
  - `CANCEL`

### 2.4 当前未写入 history 的动作

以下动作目前能改业务数据，但没有同步写入 `brain_manuscript_review_history`：

- `create`
- `update`
- `addResource`
- `disableResource`
- `addVideoMark`
- `disableVideoMark`

这意味着当前代码虽然有 timeline 查询能力，但以下业务动作不会留下对应时间线记录：

- 新增草稿/新增单据
- 修改表单内容
- 新增附件/视频
- 新增外链
- 停用附件
- 停用外链
- 新增视频标注
- 停用视频标注

## 3. 根因判断

### 3.1 根因不是“缺 history API”

- 根因不在 controller 层。
- 根因在 `ManuscriptReviewService` 的实现范围：
  - 已把历史写入封装为内部 helper
- 但只覆盖了提交、再次提交、撤销、持证跳级
- 没有把“表单更新/资源生命周期/标注生命周期”纳入同一套 history side effect
- 并且当前连 `disableVideoMark` 业务动作本身都还没有落到 service/controller

### 3.2 根因也不只是“少几行 insert”

- 当前 `R6.6` 的完成记录只宣称补了：
  - 提交
  - 再次提交
  - 持证跳级
  - 撤销
  的自然语言时间线写入。
- 它没有宣称“修改表单留痕已闭环”。
- 因此这是一个真实缺口，不是读文档误解。

### 3.3 测试面没有把这条需求锁住

- `ManuscriptReviewServiceTest` 当前会断言：
  - 主表写入
  - 资源表写入
  - 标注表写入
  - 校验拦截
- 但没有把以下断言做成失败门槛：
  - `update` 后必须 `historyMapper.insert(...)`
  - `addResource` 后必须 `historyMapper.insert(...)`
  - `disableResource` 后必须 `historyMapper.insert(...)`
  - `addVideoMark` 后必须 `historyMapper.insert(...)`
  - `disableVideoMark` 后必须 `historyMapper.insert(...)`

所以这条需求没有被测试保护住。

## 4. 风险

- 时间线对业务方是“残缺真实”：
  - 能查到部分流程动作
  - 查不到关键资料变更
- “历史参与人”判定存在偏差风险：
  - 当前详情权限判定会从 history 里收集历史参与人
  - 若某用户只发生“修改资料/追加资源/停用资源”而未触发其他写 history 动作，则其参与痕迹可能缺失
- 若继续前推页面联调，会把“有时间线接口”误当成“时间线已完整可信”

## 5. Decision

- 决策 1：
  - 不新增独立的对外 history 写接口。
  - history 继续保持为业务服务内部自动写入。
- 决策 2：
  - 下一包必须补齐以下动作的 history side effect：
    - `CREATE`
    - `UPDATE`
  - `RESOURCE_ADD`
  - `RESOURCE_DISABLE`
  - `VIDEO_MARK_ADD`
  - `VIDEO_MARK_DISABLE`
- 决策 3：
  - `UPDATE` 不能只写“已修改”空文案。
  - 至少要输出业务可读的修改摘要。
  - 若本轮不扩 response 字段，也应先保证 `actionText` 可读；如有差异明细，再写入 `extJson`。
- 决策 4：
  - 本轮不把 BPM 审批通过/退回/驳回 runtime 写回混入此修复包。
  - 这些仍留在 shared/BPM 接缝包处理。

## 6. 推进方案

- 新建下一执行包：`WP6-B3 更新留痕闭环`
- 范围只锁在后端 manuscript-review 私有/最小 shared 接缝：
  - `ManuscriptReviewService.java`
  - 必要的 history action 常量或 helper
  - `ManuscriptReviewServiceTest.java`
  - 如需验证详情时间线读出，再补 `ManuscriptReviewReadableServiceTest.java`

  - `disableVideoMark`
- 本包不做：
  - 前端页面改造
  - BPM runtime 深层闭环
  - 新增对外 history controller API
  - 重新打开 `WP7-*`

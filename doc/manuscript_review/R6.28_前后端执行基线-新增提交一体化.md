## 1. 本轮新的唯一执行基线是什么

本轮唯一执行基线可以压缩成一句话：

> 先按 `R6.26` 的完整覆盖版冻结契约收口后端，再按 `R6.27` 的新测试口径跑 fresh 证据，最后才定义前端最小工作包；当前前端不能报“进行中接近完成”。

展开后，固定口径如下：

1. 新增页“提交”是一个业务动作。
2. 修改页“保存”也是一个业务动作，但只做保存，不推 BPM。
3. “去审批”和“重新提交”仍是两个独立的后置流程动作。
4. 后端本轮收口不只看新增流程，还必须同时收口：
  - 用户新增流程
  - 用户修改并审批流程
  - 用户修改并重新提交流程
5. 当前后端汇报口径只能写：
  - 已基本到达 `WP6-G1` 最小验收阶段门口
  - 但还缺按新冻结口径跑出的 fresh runtime 证据
  - 因此不能直接判“通过”
6. 当前前端汇报口径只能写：
  - 尚未开始开发
  - 只能定义最小工作包
  - 不能写成“进行中接近完成”

## 2. 为什么旧 `R5.7 / R6.8` 不再直接作为当前执行入口

不是说旧文档没价值，而是它们不能再直接驱动这轮执行。

原因只有两个：

### 2.1 旧执行口径和新冻结契约正面冲突

旧执行链默认是：
- 新增保存
- 单独提交发起
- 资源动作独立穿插

但 `R6.26` 已经把以下内容重定义了：
- 新增提交一体化
- update 保存一体化
- 资源跟随新增提交 / 修改保存收敛
- 去审批 / 重新提交后置分流

所以凡是建立在“保存/提交分离”上的旧执行安排，都不能再拿来直接指挥当前代码和验收。

### 2.2 旧测试思路也已经被替换

`R6.27` 已经明确废弃只围绕“新增提交流程”的旧测试口径，改成覆盖三条流程。

所以从现在开始：
- `R6.26` 负责冻结业务契约
- `R6.27` 负责冻结测试口径
- `R6.28` 负责冻结执行顺序

旧 `R5.7 / R6.8` 只保留为历史参考，不再是当前执行入口。

## 3. 当前阶段判断

### 3.1 后端当前阶段

当前后端口径必须统一写成：

> 后端已基本到达 `WP6-G1` 最小验收阶段门口，但还不能直接判“通过”。

原因如下：

1. 后端目标已经足够具体，不再是模糊开发：
  - 新增提交一体化
  - update 保存一体化
  - 去审批 / 重新提交后置分流
  - 持证 / 非持证 history 条数与顺序
  - 审批通过 `APPROVE`
2. `R6.27` 已经把后端最小通过面定义清楚，可直接拿来验收。
3. 但只要还没有 fresh HTTP / SQL / BPM 证据，就不能写“后端通过”。

所以当前后端只能写：
- 接近最小验收
- 正在收口
- 必须靠 fresh 运行证据盖章

不能写：
- 后端已通过
- 可直接放行整体验收

### 3.2 前端当前阶段

当前前端口径必须写死成：

> 前端尚未开始开发。

这里不能再写成：
- 进行中
- 已有一部分
- 接近联调
- 只差收尾

原因很简单：

1. `R6.26` 已经把新增页、修改页、详情页动作口径都重定义了。
2. `R6.27` 也明确写了，前端当前只能列缺口，不能给通过。
3. shared 输出形态本轮又明确不能直接改口。

所以前端当前不是“快好了”，而是：
- 业务口径已定
- 测试目标已定
- 但页面实现尚未按新口径正式起步

当前 gate 只能统一成下面这句话：

- 前端：规则和测试都定了，但还没正式开发

因此当前 gate 结论只能是：

## 5. 可执行顺序

本轮执行顺序必须固定，不要再来回跳。

### 第一步：后端按新冻结契约收口

先做：
- 新增提交一体化收口
- update 保存一体化收口
- 去审批 / 重新提交分流收口
- 持证 / 非持证 history 条数收口
- 持证 history 顺序收口
- `APPROVE` history 文案收口

这一阶段只看后端，不抢前端页面实现。

### 第二步：后端 fresh 验证

后端改完以后，立刻按 `R6.27` 的后端最小通过面跑 fresh 证据：
- HTTP
- SQL
- BPM 节点
- history

这一步没跑完前，不得写“后端通过”。

### 第三步：代码 review

后端有了代码和初步验证后，再进 review：
- 结构是否符合 brain-system 风格
- service 是否接口/实现拆分
- 魔法值是否枚举化
- 注释、实体字段注释、Alibaba 规范是否到位

这一阶段不代替运行验证，只是质量闸门。

### 第四步：前端进入最小工作包

只有前三步完成后，才允许正式定义前端最小工作包。

注意：
- 这里是“定义工作包并开始开发”
- 不是“默认前端已经在开发中”

## 6. 前端下一步最小工作包

前端下一步只做最小闭环，不做扩写。

建议固定成 6 个最小动作：

1. 新增页只保留一个“提交”业务动作。
2. 新增页上传附件后只暂存上传结果，不写业务资源。
3. 新增页未提交前删除附件，走 `DELETE /resource/oss/{ossId}`。
4. 修改页只保留一个“保存”业务动作，保存时整表单一次性提交。
5. 详情页把“去审批”和“重新提交”做成两个独立动作。
6. 新增页、修改页、详情页按 `R6.26` 的串联方式收口页面跳转和结果判断。

前端这个包的验收目标不是“页面都做好了”，而是：
- 动作发对
- 参数带对
- 删除边界对
- 页面跳转对

只要这 4 件事没有 fresh 证据，就不能给前端通过结论。

## 7. 后端下一步最小工作包

后端下一步也只做最小收口，不扩新功能。

建议固定成 6 个最小动作：

1. 把新增提交收口成一个事务动作。
2. 把 update 保存收口成一个事务动作，但不推 BPM。
3. 把本次追加资源只在新增提交 / 修改保存时入库。
4. 把非持证新增 history 收口成 `1 条 CREATE`。
5. 把持证新增 history 收口成 `CREATE -> SKIP_LEVEL_1`。
6. 把一级 / 二级审批通过 history 收口成可读 `APPROVE`。

后端这包完成后，必须立刻进入 fresh 验证，不允许停在“代码看起来差不多”。

## 8. 缺口怎么分层写

为了避免把缺口混成一团，本轮缺口必须分 4 层写。

### 8.1 shared / 接口缺口

只写这类问题：
- 当前 `submitAndFlowStart` 是否能承接主表 + 附件 + 外链
- 当前 `PUT /workflow/manuscript-review` 是否能承接主表 + 追加资源参数
- 当前详情是否有足够的“去审批”跳转信息

这层缺口的结论只能是：
- 已对齐
- 未对齐
- 待收口

### 8.2 runtime 缺口

只写这类问题：
- 新增提交事务是否真的一次性落库
- update 保存事务是否真的不改 BPM
- history 条数和顺序是否真的符合新契约
- BPM 是否真的落到一级 / 二级 / 三级节点

没有 fresh 运行证据，就不能写通过。

### 8.3 browser 缺口

只写这类问题：
- 前端是否真的只剩一个新增“提交”动作
- 前端是否真的只有一个修改“保存”动作
- 删除附件是否真的走 `DELETE /resource/oss/{ossId}`
- 详情页是否真的把“去审批 / 重新提交”分流开

前端没开始开发，就要实写“未开始 / 待开发 / 待浏览器验证”。

### 8.4 验收缺口

只写这类问题：
- 即使后端通过了，前端没开发，整体验收是否仍不能通过

这层的结论要最保守：
- 后端可接近通过
- 整体验收不能通过

## 1. 当前唯一执行口径

### 1.1 基线来源

当前验收必须同时满足以下两层基线：

1. `WP6-G1` 既有 gate 目标仍有效：
  - 本轮是 gate 复核/验收，不是新功能开发
  - 不参考旧失败实现
  - `brain-manuscript-review` 只作为代码落点，不作为实现基线
  - 若证据不足，只能报缺口，不能脑补“通过”
2. `R6.26 ~ R6.28` 将 `WP6-G1` 的后端验收口径重写为：
  - 新增页“提交”是一个业务动作
  - 修改页“保存”也是一个业务动作，但不推 BPM
  - “去审批”和“重新提交”仍是两个独立后置动作
  - 后端验收不再只看新增流程，必须同时覆盖：
    - 用户新增流程
    - 用户修改并审批流程
    - 用户修改并重新提交流程

### 1.2 本轮不允许做的事

- 不回退到 `R5.7 / R6.8` 的“保存/提交分离”旧口径。
- 不把当前代码行为反推成冻结契约。
- 不因为前端未开始就把后端“接近完成”写成“已通过”。
- 不把这轮扩成前端实施、shared 改造或新一轮设计。

## 3. 本轮验收范围

### 3.1 纳入验收

1. 新增并提交一体化：
  - 有资源场景
  - only-external-link 场景
  - 非持证发起人

  - history 表

  - `flow_task`

### 3.2 不纳入“通过”结论

- 未提供 fresh 运行证据的推断结论

## 4. 验收顺序

### 第一步：P0 blocker 先行复核

先只验证 4 件事：

1. 新增提交后是否仍写出 `SUBMIT / RESOURCE_ADD`
2. 持证跳级后是否仍错误写出一级 `APPROVE`
3. `current_node_label` 是否与冻结业务文案一致
4. 新一体化主路径是否有足够单测覆盖

这一步只要任一项失败，就不能给后端“通过”。

### 第二步：后端最小通过面用例

按 `R6.27` 跑：

1. `BE-01` 非持证新增提交
2. `BE-02` only-external-link 新增提交
3. `BE-04` 持证新增提交
4. `BE-06` 修改保存一体化
5. `BE-08` 修改保存后重新提交
6. `BE-09 / BE-10` 一级 / 二级审批通过可读 `APPROVE`

### 第三步：结果归档

结果输出只允许三种：

1. `通过`
  - 仅当 fresh HTTP + SQL + BPM + history 四链同时满足新口径
2. `未通过`
  - 已有 fresh 证据证明与冻结契约冲突
3. `待确认`
  - 证据链缺失，不能判

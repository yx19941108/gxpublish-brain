## 1. 是否需要新基线

- 结论：`需要`

原因如下：

- `R5.7_第6-7轮执行基线.md` 仍然有效，但它只够做“宏观执行边界”基线，不够继续支撑当前编码。

  - `WP6 shared 接缝最小整改阶段有条件通过`
  - `冻结口径未整体闭合`
  - `R7 暂不放行`
- `R6.6` 又把 `WP6-B2` 状态限定为：
  - private 能力补齐了一批关键缺口
  - 但仍有 workflow/BPM runtime blocker
- `R6.7` 新增审计已确认：
  - history 表和查询链存在
  - 但 create/update/resource/mark 没有完整写 history

因此：

- `R5.7` 不能再单独作为继续编码入口。
- 从本轮开始，`R6.8` 才是下一会话唯一执行入口。

## 5. WP6-B3 目标

- 唯一目标：
  - 把“更新审校表单要留历史记录”落实成后端闭环

必须补齐的动作：

- `CREATE`
- `UPDATE`
- `RESOURCE_ADD`
- `RESOURCE_DISABLE`
- `VIDEO_MARK_ADD`
- `VIDEO_MARK_DISABLE`

最低交付要求：

- 每个动作发生后都向 `brain_manuscript_review_history` 写入一条记录
- `actionType` 可机读
- `actionText` 业务可读
- `UPDATE` 至少能体现修改摘要
- 读链 `timelineItems` 能读到这些新增记录
- 当前代码尚缺 `disableVideoMark` 业务动作本体；本包必须先把该动作补出来，再补其 history

## 8. 实施规则

### 8.1 写入规则

- `create`：
  - 写 `CREATE`
- `update`：
  - 写 `UPDATE`
  - 必须有业务可读修改摘要
- `addResource`：
  - 写 `RESOURCE_ADD`
  - 至少区分附件/视频/外链
- `disableResource`：
  - 写 `RESOURCE_DISABLE`
  - 文案需体现停用对象
- `addVideoMark`：
  - 写 `VIDEO_MARK_ADD`
- `disableVideoMark`：
  - 写 `VIDEO_MARK_DISABLE`
  - 文案需体现停用的标注对象

### 8.2 精度规则

- 不允许只写“已修改”“已处理”这类空泛文案
- 不允许只改业务表，不落 history
- 不允许只补 history insert，不补测试
- 不允许为了留痕而新开外部 API
- 不允许跳过 `disableVideoMark`，把“停用视频标注”继续留在文档口径里但代码不实现

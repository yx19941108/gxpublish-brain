# 审校模块需求到测试映射评审 v01

## 1. 边界与已确认

- 唯一需求真源：`doc/manuscript_review/product/20260321_manuscript-review_product-requirements_v01.md`
- 本评审不引用旧 editorial 业务实现，不将旧实现语义视为兼容基线。
- 已确认平台事实可直接使用：当前数据库仅有平台通用表，尚无 manuscript-review 业务表；后端定向命令已进入真实 `testCompile` RED；前端路由壳测试仍停在 `window is not defined` harness RED。

## 2. 总体评审结论

- PRD 已足以驱动一套严格的 RED-first 测试设计，且可以先从后端规则、SQL 能力缺口、前端壳层约束三线启动。
- 当前最容易失真的不是 happy path，而是三类边界：
  1. 草稿/删除语义被习惯性混入一期。
  2. 列表、详情、历史、办理流转中泄露技术 ID、账号、原始枚举码。
  3. “当前有效资源”与“追加历史可追溯”被实现成覆盖更新或软删除后不可追溯。

## 4. 首批必须守住的拒绝性验收口径

- 不接受任何“先放草稿、删除占位，后续再关”的实现。
- 不接受任何“接口先返回 ID/账号，前端再自己翻译”的方案。
- 不接受任何“资源修改先覆盖旧值，历史以后补”的方案。
- 不接受把“持证”当作稿件基本信息长期保存并展示给业务用户。
- 不接受把“修改 + 再次提交”或“修改 + 去审批”合并成单动作。

## 5. 最高风险验收缺口

- 最高风险缺口：`列表/详情/历史/资源区/BPM 分流` 的统一业务可读契约尚未被一个端到端验收链同时锁死。若只分别验证后端规则或前端页面，很容易出现“流程能跑，但接口或页面仍泄露技术 ID/账号/原始码值，且把追加历史错误做成覆盖更新”的伪通过。
